# Методические рекомендации преподавателю: проектная работа

**Дисциплина:** Прогнозирование временных рядов: от статистики до MLOps  
**Архитектура ФОС:** ЛР1–10 = milestones **одного** группового проекта; PRC = финальная защита MVP  
**Система оценивания:** [docs/grading.md](../docs/grading.md)

Проектная работа организована как **сквозной индустриальный кейс**: на **1-й учебной неделе** команда выбирает **один** релевантный массив данных и проводит его через все этапы инженерного цикла — от EDA до контейнеризованного прогнозного сервиса с мониторингом. Смена кейса после утверждения [устава](templates/project_charter.md) — только по согласованию с преподавателем.

---

## 1. Роль преподавателя

Преподаватель выступает **научным руководителем** сквозного проекта:

- формирует команды 3–4 чел. и распределяет кейсы партнёров;
- контролирует сдачу **milestones ЛР1–10** и минимальные требования;
- модерирует коммуникацию «команда ↔ партнёр»;
- оценивает milestones, COP, PRC и организует **peer-review**;
- организует финальную защиту.

Партнёр оценивает **предметную ценность** MVP; преподаватель — **методическую корректность**, полноту цикла и соответствие КРМ.

### 2.1. Темы сквозного проекта для команд

Методически предусмотрены **две альтернативные темы** на основе задач индустриальных партнёров. Команда выбирает **одну** и фиксирует её в уставе до kick-off.

#### Вариант 1. «Интеллектуальный мониторинг и упреждающее прогнозирование утилизации ресурсов ИИ-кластеров»

**Партнёр / контекст:** облачный ИТ-провайдер (Т1).

**Бизнес-проблема:** высокие затраты на простой GPU/CPU и риск деградации смежных сервисов при пиковых всплесках нагрузки во время обучения тяжёлых моделей. Нужен **упреждающий** прогноз для автоматического масштабирования.

**Характер данных:** высокочастотный промышленный трейс логов распределённых систем (открытый аналог — **Alibaba Cluster Data**): поминутная дискретизация, аномальные пики, **concept drift** при смене паттернов нагрузки.

**Ключевая задача прогноза:** многомерная нагрузка кластера (**CPU, RAM**) на **1 час вперёд** с шагом **5 минут**.

**Специфика MLOps (ожидания к MVP):**

- обнаружение аномалий во входящем потоке метрик/логов;
- триггер **retraining** (Airflow / Prefect) при фиксации drift;
- оповещения при выходе прогноза за **критические пороги**.

**Итоговый MVP:**

- REST API (FastAPI), эндпоинт прогноза нагрузки (например `/predict_load`);
- приём текущего потока метрик → прогноз на горизонт;
- алерт дежурной смене (Telegram-бот, email или аналог);
- дашборд текущего и прогнозного состояния (опционально на уровне «П»).

#### Вариант 2. «Прогнозирование спроса на сезонные товары с динамическим промо-контуром»

**Партнёр / контекст:** SM Lab / розничная сеть (Спортмастер).

**Бизнес-проблема:** логистические потери из-за «сезонных шоков» (погода) и хаотичных скидок — **дефицит** на полке или **перезатаривание** склада.

**Характер данных:** ежедневные объёмы продаж по товарным группам, календарь акций и праздников, внешние факторы (открытый аналог — **M5 Forecasting Accuracy**): выраженная сезонность, пики в праздники, зависимость от промо.

**Ключевая задача прогноза:** **посуточный** спрос (товарооборот) по ключевым категориям на **14 дней** вперёд.

**Специфика MLOps (ожидания к MVP):**

- интеграция **exog**: план промо-акций и (по возможности) прогноз погоды;
- логирование экспериментов в **MLflow**;
- опционально: **Quantile Loss** / квантильный прогноз (штраф за недовоз выше, чем за избыток).

**Итоговый MVP:**

- REST API (FastAPI), эндпоинт прогноза спроса (например `/predict_demand`);
- JSON-запрос с **планом скидок** на 2 недели (+ exog при наличии);
- расчёт рекомендуемого объёма поставок;
- дашборд для категорийного менеджера: прогноз vs факт, риски дефицита.

> Обе темы проходят **одинаковые четыре продуктовые вехи** и milestones **ЛР1–10**; отличаются постановка, частота ряда, exog и акценты MVP (см. §7).

### 2.2. Четыре продуктовые вехи (соответствие ЛР1–10)

Какой бы кейс ни выбрала команда, данные проходят **четыре последовательные вехи**:

| Веха | Milestones | Содержание | Результат этапа |
|------|------------|------------|-----------------|
| **1. Разведочный анализ и очистка** | ЛР1–2 | Сырой массив партнёра: очистка от сбоев и пропусков; графики ACF/PACF; сезонность (суточная, недельная, календарная); тесты стационарности (ADF/KPSS) | Очищенный массив, готовый к моделированию; `data/processed/` |
| **2. Статистическое и ML-моделирование** | ЛР3–6 | SARIMA (подбор параметров, диагностика); регрессия с лагами и exog; **CatBoost / LightGBM / XGBoost** со скользящими окнами | Сравнительная таблица stat vs ML на едином test |
| **3. Глубокое обучение и устойчивость** | ЛР7–8, COP | **LSTM/GRU** (PyTorch) для многошагового прогноза; HPO (Optuna); **стресс-тест** — симуляция резкой смены условий (drift), оценка деградации | `best_model`, правила drift и retraining; участие в Forecast Cup |
| **4. Инфраструктура и prod-мониторинг** | ЛР9–10, PRC | Лучшая модель → **REST API** + **Docker** + **MLflow**; логирование; сценарий **автоматического retrain** при падении качества | Контейнеризованный сервис, demo на защите |

На каждой вехе преподаватель проверяет не только «галочку ЛР», но и **связность** с бизнес-постановкой выбранной темы (§2.1).

## 5. Работа с индустриальным партнёром

### Роли партнёров по методическим темам

| Тема | Что ожидать от «заказчика» на защите |
|------|-------------------------------------|
| **Вариант 1 (Т1)** | Ценность **упреждающего** масштабирования; пороги CPU/RAM; реакция на ложные алерты |
| **Вариант 2 (SM Lab)** | Логистика и промо; асимметрия ошибки (дефицит vs излишек); интерпретация 14-дневного горизонта |

Если партнёр участвует только письменно — передайте команде **2–3 вопроса** из его домена для блока Q&A на PRC.

### Ожидания от партнёра

- Kick-off 1 встреча (30–60 мин); контакт **координатора** команды.
- Ответ по данным ≤ 5 раб. дней.
- Участие в финальной защите или письменный feedback.
- Не требовать production SLA от учебного MVP.

### Ожидания от команды

- Конфиденциальность данных (**Data Analyst** отвечает за `.gitignore`).
- Итеративные демо после milestones (не «big bang» на PRC).
- MVP — прототип с roadmap post-MVP.

### Если партнёр «пропал»

1. Резервный кейс: **ENTSO-E** + proxy-постановка в уставе.
2. При оценке **PRC** снизить балл за **презентацию (D)** или **документацию (E)**, если партнёр не участвовал; технические ЛР1–10 и MVP — без снижения весов.
3. На защите преподаватель выступает как «заказчик».

## 6. Оценивание

### 6.1. Итоговая структура (дисциплина)

| Компонент | Вес | Где оценивает преподаватель |
|-----------|-----|----------------------------|
| Milestones **ЛР1–10** | **40 %** (10 × 4 %) | Файлы ЛР + отчёт команды; rubrics §3 в [rubrics.md](rubrics.md) |
| **ПЗ1–5** | **10 %** (5 × 2 %) | LMS; ключи `*_key.md` |
| **COP** | **15 %** | 50 % leaderboard + 50 % отчёт |
| **PRC + peer-review** | **35 %** | [rubrics.md](rubrics.md) §1 × \(k_{peer}\) из [peer_review.md](peer_review.md) |

Подробно: [docs/grading.md](../docs/grading.md).

> **Не используйте** устаревшую схему «Milestone 1/2/3 + 35 % защита» — актуальная структура: ЛР1–10 + PRC + peer-review.

### 6.2. Оценивание одной ЛР (4 %)

| Уровень | % | Дескриптор (кратко) |
|---------|---|---------------------|
| Базовый | 60 | Milestone сдан, минимальные артефакты |
| Средний | 80 | Полный объём, код в repo, корректные выводы |
| Продвинутый | 100 | Глубина, воспроизводимость, готовность к следующему этапу |

**Вклад в зачёт:** `4 % × (уровень / 100)`.

### 6.3. PRC (35 %) и peer-review

Оценка MVP на защите — **пять осей** (сумма 100 %), см. [rubrics.md](rubrics.md) §1:

| Ось | Вес | Кратко |
|-----|-----|--------|
| **A. Полнота функционала** | 30 % | Прогноз в реальном времени / по запросу; API без критических ошибок; нет утечки данных |
| **B. Код и архитектура** | 20 % | Модульный сквозной pipeline, воспроизводимый repo |
| **C. Мониторинг и retraining** | 20 % | Отслеживание качества; автоматизация или playbook retrain при drift |
| **D. Презентация и Q&A** | 15 % | Бизнес-эффект для Т1 или ритейла; понимание математики моделей |
| **E. Документация** | 15 % | Развёртывание **без участия авторов** (README, DEPLOY.md, API) |

Процедура начисления:

1. Выставите **командную** оценку PRC по rubrics §1 (критерии A–E, сумма = 100 %).
2. Переведите в 35 % дисциплины: `35 % × (балл / 100)`.
3. После peer-review умножьте на **\(k_{peer}\)** (0,7–1,3) — см. формулы в [peer_review.md](peer_review.md).

### 6.4. Индивидуальный вклад

- На **PRC** каждый участник ≥ 2 мин по своей роли (Data Analyst / ML Engineer / ML Researcher / MLOps).
- **Free-rider:** мало commits, не отвечает по зоне → снижение \(k_{peer}\), не автоматическое «−1 уровень» всей команде.
- **ПЗ1–5** — строго индивидуальны; не смешивать с оценкой milestone.

### 6.5. Минимальные пороги зачёта

См. [grading.md §6](../docs/grading.md):

- ≥ 7 из 10 milestones ЛР на уровне не ниже «Базовый»;
- ≥ 1 submission COP;
- защита PRC (demo);
- заполнен peer-review (≥ 3 анкеты на команду из 4 чел.).

## 7. Организация защиты PRC

### Состав комиссии

- Преподаватель (председатель).
- Представитель партнёра (желательно): Т1, SM Lab или свой кейс.
- Опционально: второй преподаватель / аспирант.

### Тайминг (на команду)

| Блок | Время | Кто |
|------|-------|-----|
| Презентация | 10–15 мин | все (≥ 2 мин каждый) |
| Demo MVP | 5 min | **MLOps** (+ ML Engineer) |
| Вопросы | 10 min | комиссия |

### Обязательные вопросы (общие)

1. Бизнес-задача и **метрика успеха** для выбранной темы (§2.1)?
2. Почему выбрана финальная модель (`best_model`)?
3. Протокол валидации — где test, нет ли утечки?
4. Прогноз через API (**live demo**).
5. План при data/concept drift ([ЛР8](../M3-neural-networks/lab08_validation_drift.md), [ЛР10](../M4-infrastructure-and-deployment/lab10_monitoring.md))?

### Дополнительные вопросы по теме

**Вариант 1 (кластер):**

- Какой **горизонт и шаг** прогноза (1 ч / 5 мин)? Как агрегировали поминутный ряд?
- Покажите сценарий **пика** или аномалии — сработал ли алерт?
- Как устроен **retraining** при concept drift (триггер, DAG, пороги)?

**Вариант 2 (ритейл / промо):**

- Как учтены **промо и календарь** в модели (exog, лаги)?
- Прогноз на **14 дней** — одна категория или агрегат? Почему?
- Как интерпретируете ошибку для бизнеса (дефицит vs перезапас)? Использовали ли quantile / асимметричную метрику?

### Чек-лист demo для комиссии

| Проверка | Вариант 1 | Вариант 2 |
|----------|-----------|-----------|
| API поднимается по `DEPLOY.md` | ✓ | ✓ |
| Эндпоинт прогноза | `/predict_load` или эквивалент | `/predict_demand` или эквивалент |
| Exog на входе | поток метрик / окно history | JSON с **планом промо** (+ погода опц.) |
| MLflow / версия модели | ✓ | ✓ |
| Drift или retrain (хотя бы симуляция) | ✓ | ✓ |
| Дашборд / алерт | желательно | желательно |

После защиты — открыть **peer-review** на 48–72 ч.

## 8. Типичные проблемы и решения

| Проблема | Действие |
|----------|----------|
| Команда не бьёт baseline (ЛР3) | EDA (ЛР1–2), упростить $h$, ES + признаки |
| MVP не собирается в Docker (ЛР9) | Extension только при working local API; MLOps + office hours |
| Конфликт / free-rider | RACI в charter, git log, peer-review |
| Партнёр дал не time series | Агрегация по времени или смена кейса |
| Команда выбрала Alibaba, но не тянет объём | Подвыборка одного узла / недели; Kaggle-сборка 1 ГБ |
| M5 слишком большой | Одна `item_id` / категория в уставе; фиксированный store |
| «Координатор делает всё» | Напомнить RACI; оценка по ролям на milestones |
| LLM без понимания | Опрос на защите; см. [project_guidelines §10](project_guidelines.md) |
